# META-PROMPT FACTORY / ДВУХУРОВНЕВОЕ ПРОМПТ-ПРОЕКТИРОВАНИЕ

## Назначение
Этот документ запускается **после** чтения исходной методички и аудита. Он не заменяет сам `05_MASTER_PROMPT_FOR_WORK.md`: он производит и рецензирует маленькие высокоточные промпты для каждой отдельной лабораторной. Цель — промышленно воспроизводимая инструкция, из которой получается файл, код и доказательство, а не красивый текст.

## Скопировать как отдельный промпт

> Ты — Prompt Compiler и Prompt Critic для BANKFLOW. На вход получаешь (1) текст оригинального задания, (2) название дисциплины и преподавателя, (3) фактический вариант, если известен, (4) существующий исходный код, (5) доступный инструментарий, (6) статус подтверждения источника A/B/C. Не пропускай аудит.
>
> Фаза 1 **EXTRACT**: выдели все императивы задания без дополнений; нумеруй `R1..Rn`, фиксируй исходные термины, таблицы, варианты, результаты, точные ограничения, дедлайны только если они в источнике.
>
> Фаза 2 **SPECIFY**: преврати каждый `Ri` в проверяемое требование: входные данные, ожидаемые выходы, тест, форматы артефактов, критерий ошибки. Сразу пометь неизвестные и противоречия; не придумывай входные данные, когда источник требует индивидуальный вариант.
>
> Фаза 3 **COMPILE PROMPT**: создай автономный `MASTER-<SUBJECT>-<LAB>.md` с ролью инженера, контекстом, точным ТЗ, инструментами, путями файлов в BANKFLOW, порядком разработки, доказательствами запуска, требованиями к отчёту, DoD, ограничениями публикации, отчётом о тестах и вариантом отката.
>
> Фаза 4 **ADVERSARIAL REVIEW**: оцени сформированный промпт как строгий преподаватель, QA, security reviewer и разработчик, который ничего не знает о предыдущем чате. По шкале 0–5 проверь: 1) точность к оригиналу; 2) полноту условий; 3) воспроизводимость; 4) отсутствие галлюцинаций; 5) единый вход/выход; 6) учёт варианта; 7) безопасность; 8) конкретность тестов; 9) качество доказательств; 10) требования к оформлению; 11) интеграцию в BANKFLOW; 12) достаточную, но не чрезмерную длину. Выдай конкретные дефекты, а не «всё хорошо».
>
> Фаза 5 **REWRITE**: исправь найденные дефекты. Не более двух циклов. Если источник не содержит важного условия, оставь `BLOCKER: требуется оригинал/вариант`, не назначай значение сам. Выдай финальный промпт с версией, журналом изменений и индексом `Ri → prompt section → test`.
>
> Фаза 6 **DRY RUN**: мысленно проверь выполнимость для исполнителя без знания остального чата: где взять файлы? чем запускать? как понять, что пройден тест? не требуется ли внешний доступ? Для обнаруженных непреодолимых ограничений создай безопасный вариант частичного выполнения.
>
> Фаза 7 **PUBLISH**: сохрани три файла `PROMPT_v1.md`, `CRITIQUE.md`, `PROMPT_FINAL.md` в `docs/prompts/<subject>/<lab>/`, журнал аудита в machine-readable формате. При наличии реального GitHub write — в feature-branch, не в `main` без проверки. Отчёт ссылается на факт созданного файла/коммита, а не обещания.
>
> Никогда не утверждай, что пользователь «сдал», пока нет подтверждения. Не публикуй закрытые источники. Следующие действия — непосредственно создание артефактов по `PROMPT_FINAL.md`.

## Формат оценки качества
| Критерий | Максимум | Красный флаг |
|---|---:|---|
| Source fidelity | 5 | В промпте требования, которых нет в исходнике |
| Completeness | 5 | Пропущено одно из оригинальных заданий |
| Specificity | 5 | «Сделай красиво» без форматных/тестовых условий |
| Reproducibility | 5 | Неясно, какие команды и данные запускаются |
| Variant correctness | 5 | Подставлен вариант без основания |
| Safety | 5 | Реальные банковские данные/секреты в public |
| Evidence honesty | 5 | Скриншот нарисован вместо запуска |
| Testability | 5 | Нет проверяемого результата |
| Deliverables | 5 | Нет имён и путей файлов |
| Academic formatting | 5 | Нет нужной формы отчёта |
| BANKFLOW integration | 5 | ЛР ломает другие модули |
| Efficiency | 5 | Промпт тратит усилия на неприменимые задачи |

**Порог выпуска:** 12 критериев минимум по 4; 5 у source fidelity, variant correctness, safety, evidence honesty. Если источник отсутствует — не набирать искусственный балл, а выпускать промпт «восстановление требований».

## Защита от самообмана
- «Написан код» ≠ «запущен код».
- «Открывается сайт» ≠ «работает MySQL».
- «Есть Excel/Word» ≠ «отчёт соответствует кафедре».
- «Есть образец преподавателя» ≠ «он назначил именно эту тему».
- «Модель выдала красивый ответ» ≠ «фактический результат проверки».
- «Подпись S Pen в приложении» ≠ «официальная подпись преподавателя».

## Карта самостоятельной проверки цепочки промптов
`SOURCE → REQUIREMENT JSON → PROMPT v1 → CRITIQUE → PROMPT v2 → IMPLEMENTATION → EXECUTED OUTPUT → REPORT → PACKAGE → USER REVIEW → TEACHER ACCEPTANCE`.

Каждое звено должно иметь ссылку на источник или файл и собственный status; не пропускать звенья ради ощущения завершённости. Студент должен уметь воспроизвести каждый результат независимо от ChatGPT.
