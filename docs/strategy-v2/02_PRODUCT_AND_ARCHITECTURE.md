# BANKFLOW NEXT — Product Requirements & Architecture
**Статус:** предлагаемый документ версии 2.0. Исходная v1.2 остаётся стабильной, миграция только после тестов.

## 1. Product vision
BANKFLOW — единственная точка входа в учебную информационную систему: синтетическая банковская предметная область + семь профильных дисциплин + восьмой пункт учебного плана + личный процесс сдачи. Главная метафора: **«рабочее место инженера, а не презентация»**.

**Три режима:**
1. **Демонстрация** — красивый, детерминированный сценарий с вымышленными данными, работает без интернета.
2. **Лаборатория** — оригинальное условие → решённый пункт → реальный код → контрольный вход и выход → фактические скриншоты/логи.
3. **Сдача** — документы, проверка комплектности, ZIP одной дисциплины/ЛР, ручное подтверждение передачи и приёмки.

**Не цели:** банковские платежи, реальные персональные/банковские данные, подключение к инфраструктуре ПСБ, имитация принятия лабораторной, замена Access/MySQL/Colab/Express на HTML-демо там, где преподаватель требует именно их.

## 2. Пользователи и маршруты
| Роль | Задача | Контрольный сценарий |
|---|---|---|
| Студент | быстро увидеть, что осталось | Dashboard → дисциплина → одна работа → доказательства → экспорт |
| Преподаватель при демонстрации | посмотреть только свою дисциплину | демонстрационный режим → предмет → Live Demo → исходный код → проверяемый результат |
| Студент-разработчик | исправить код без потери стабильного сайта | GitHub branch → тесты → сборка → preview → main |
| Сотрудник условного банка (в модели) | регистрировать и обрабатывать обращения | найти клиента → заявка → сотрудник → изменение статуса → журнал |

## 3. Критическая архитектурная проблема v1.2
`src/build.py` встраивает в `index.html` большую часть материалов, JSON-данные и ZIP-архивы в base64. Это даёт удобную автономность, но увеличивает монолит, усложняет пофайловое кэширование, влияет на первоначальную загрузку и делает **любой вложенный файл публичным**, если сайт размещён на GitHub Pages. Текущая `src/subjects.json` представляет лабораторные массивами строк; этого недостаточно для надёжного учета источников, доказательств, вариантов и статусов.

## 4. Рекомендуемая структура v2 (без немедленного обязательного переписывания)
```text
BANKFLOW/
├── apps/
│   ├── web/                    # PWA-оболочка (статика для GitHub Pages)
│   │   ├── public/             # иконки и статические данные, проверенные на публичность
│   │   └── src/                # app shell, роутер, UI, design tokens
│   └── local-api/              # Python stdlib + SQLite; только доверенная локальная сеть
├── packages/
│   ├── domain/                 # типы/схемы клиентов, обращений и предметов
│   ├── academic-registry/      # реестр требований по дисциплинам, provenance
│   ├── export/                 # сборка изолированных пакетов сдачи
│   └── demo-fixtures/          # единые синтетические эталонные данные
├── labs/
│   ├── 01-db/                # Access/SQLite по назначенным заданиям
│   ├── 02-vmip/
│   ├── 03-iis/               # Notebook / Colab
│   ├── 04-isit/              # MySQL 8
│   ├── 05-design/            # единый документ и схемы
│   ├── 06-server/            # JavaScript/Node/Express
│   └── 07-standards/         # расчеты, сетевые графики, стандарты
├── docs/
│   ├── architecture/
│   ├── academic/
│   ├── design-system/
│   └── quality/
├── tests/                    # smoke, unit, API, browser, mobile, build
└── scripts/                  # deterministic build and release
```
Для текущего объёма необязательно внедрять тяжёлые React, TypeScript, Docker или микросервисы. Можно оставить **vanilla JS + Python stdlib** и поэтапно разнести исходники на ES-модули. Переход должен быть обратимым и не ломать статический offline-bundle.

## 5. Модель предметной области
`Client(id,name,city,segment)`; `Product(id,category,name)`; `Employee(id,name,role)`; `Request(id,client_id,employee_id,product_id,priority,status,created_at,updated_at)`; `RequestEvent(id,request_id,action,at,actor_label)` — **история действий предлагается**, сейчас не реализована. Поля данных синтетические, UUID/ID стабильные, валидируются. Не симулировать настоящие банковские операции.

**Статусы:** `Новое → В работе → Закрыто`; возвращение статуса только явно разрешённым переходом; должна быть история изменений. При отсутствии защищённой авторизации локальный API демонстрационный и не предназначен для открытой сети.

## 6. Реестр учебных требований — единый источник истины
Вместо массива `[номер, название, описание]`:
```json
{
  "subject_id": "iis",
  "lab_id": "iis-lr1",
  "title": "Инструментальные средства подготовки датасета",
  "assignment_state": "confirmed_original",
  "source": {"file": "ЛР1_Интел_системы_и_технологии_2025.ipynb", "verified": "2026-11-17"},
  "requirement_ids": ["iis-lr1-r1", "iis-lr1-r2"],
  "variant": {"value": null, "state": "needs_confirmation"},
  "implementation": "executed_local",
  "evidence": ["executed_notebook", "report_docx"],
  "submitted_at": null,
  "accepted_at": null
}
```
Каждое требование отдельно: `REQ-ID`, формулировка дословно или аккуратный пересказ, вид источника, доверие A/B/C, требуемый артефакт, тест, доказательство, остаточный риск, ответственное решение. Не конструировать работы из предположений.

## 7. Два режима данных без иллюзии синхронизации
- **Офлайн/PWA:** синтетический снимок + изменения локально. Для структурированных данных и вложений предпочтительна IndexedDB; `localStorage` оставить для мелких настроек и миграции. Добавить ручной экспорт/импорт резервной копии и понятный экран «где хранятся данные».
- **Локальный backend:** SQLite как реальная БД, отдельный Python API. Показать индикатор источника истины, количество записей, время обновления. Не обещать передачу локальных браузерных изменений в SQLite без конкретного механизма синхронизации и разрешения конфликтов.
- **Учебный MySQL:** отдельное окружение и набор команд, не связанный автоматически с SQLite.
- **Python/Colab:** отдельные исполняемые исследования с фиксированным датасетом и `requirements.txt`.

## 8. API и проектные ограничения
Существующие `/api/health`, `/api/clients`, `GET/POST/PATCH /api/requests` сохранить совместимыми. Для предложенного журнала — `GET /api/requests/{id}/events` (не реализовано). Валидация всех полей, foreign keys, запросы только параметризованные. Ограничения длины, количества элементов, пагинация при росте. Тесты некорректных ID, дублей, статусов, неизвестных методов, отсутствия соединения.

## 9. Академический конвейер сдачи
`DISCOVER → VERIFY_SOURCE → IMPLEMENT → EXECUTE → EVIDENCE → REPORT → PACKAGE → READY_FOR_REVIEW → SUBMITTED → ACCEPTED`.
- **Первые восемь стадий** — внутренние, подтверждаются артефактами/тестами.
- `SUBMITTED` — только после факта отправки пользователем/реальной регистрации передачи.
- `ACCEPTED` — только по достоверному факту от преподавателя. Нельзя устанавливать на основании наличия подписи-рисунка, зелёного цвета или статуса в приложении.
- Статус `blocked_unknown_assignment` не должен портить показатели «прогресса разработки».

## 10. Пакеты для преподавателей
`exports/{subject}/{lab}/`: точный `README.md`, версия, тема и вариант, исходники, тестовые данные, запуски/скриншоты, отчёт, зависимости, проверка целостности SHA256. Отдельный ZIP на ЛР; при сдаче нескольких ЛР — ZIP предмета. Готовая сборка не должна автоматически включать исходные методички или переписки. Нельзя публиковать закрытые исходные задания на Pages.

## 11. Подтверждение демонстрации стилусом
Сделать **опциональный** экран «Факт демонстрации» с рисованием стилусом через Pointer Events / canvas, таймстампом и названием ЛР. Подпись только добровольная, очищаемая, хранится в частном локальном хранилище, не передаётся на GitHub; рядом подпись «Личная запись о демонстрации, не официальная университетская отметка». Не хранить чужие подписи в публичном репозитории. Кнопка «Отменить» сбрасывает отметку и рисунок. Никакого автоматического перевода в `ACCEPTED`.

## 12. Safety, privacy, reliability
- Никаких реальных клиентов, историй звонков, банковских реквизитов, внутренних KPI, выгрузок ПСБ.
- Для публичного GitHub: автоматическая проверка секретов, приватных имён и материалов из закрытых чатов, лицензий и авторских прав.
- Локальный API по умолчанию только `127.0.0.1`; режим `0.0.0.0` — только доверенная LAN и только синтетика.
- Не выдавать частное хранилище PWA за защищённую БД; не обещать сохранность после очистки браузера.
- Контраст/управление с клавиатуры/пальцем и стилусом; резервный экспорт; офлайн после реально проверенной установки кэша.

## 13. Архитектурный ADR
`ADR-001`: единая статическая PWA-оболочка для демонстрации; причиной выбора является планшет и Pages.  
`ADR-002`: локальный SQLite — демонстрация реальных CRUD, не замена MySQL.  
`ADR-003`: лабораторные сохраняют исходные инструменты методичек, даже если единый портал объединяет результаты.  
`ADR-004`: источники требований — versioned JSON, отделённый от маркетингового статуса.  
`ADR-005`: приватные доказательства и подписанные формы отдельно от публичного фронтенда.  
`ADR-006`: миграция v1.2 → v2 только с проверкой совместимости и возможностью отката.
